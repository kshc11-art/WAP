## 0. 최우선 원칙 — 1차·2차 업로드 파일 보호 (v1.2 신설)

**본 도구의 존재 이유는 1차 업로드 2종과 2차 업로드 1종이다.** 리포트·스마트등급·조회용 파일·히스토리는 전부 부가 기능이며, 어떤 부가 기능도 업로드 파일의 내용을 바꾸어서는 안 된다(스마트등급의 2차 Y열 기입은 유일한 예외이자 명시된 사양 — §4.9).

유지보수 시 지켜야 할 불변식(2026-07-15 실측 증명 완료, §6.4):

1. **엔진 버전 간 무결성**: 등급 미사용 조건에서 신·구 엔진의 업로드 3종은 전 시트·전 셀(타입+값)이 동일해야 한다. (v1.2→v1.3: 2026 Q1·Q2·Q3 × 3파일 = 9회 대조, 전부 0셀 차이)
2. **담당자 실파일 대조**: 최신 분기 산출물의 관리번호 집합이 담당자 실제 업로드 파일과 일치해야 한다. (Q3: 1차 연구부서 82/82 · 1차 기술사업화그룹 60/60 · 2차 82/82 완전 일치)
3. **등급 기능의 영향 범위**: 등급 결과 파일 사용 시 변화는 2차 Sheet1의 **Y열(25) 값과 미매칭 셀의 배경/메모뿐**이어야 하며, 1차 2종은 완전 불변이어야 한다. (실측: 2차 차이 79셀 전부 Y열, 1차 0셀)
4. **분류 불변**: 스마트등급은 분류(F)에 영향을 주지 않는다. `applyGrades`는 `classify` 이후에 실행되며 `row.F`를 읽기만 한다.

**어떤 수정이든 배포 전 §6.6의 두 스크립트(`validate_v13_full.js`, `integrity_proof.js`)를 통과해야 한다.** `buildUpload1`/`buildUpload2` 본문·서식·말행중복 로직을 건드리는 변경은 특히 `integrity_proof.js`(무결성)와 §6.1 레거시 셀 대조 기준을 함께 갱신·통과해야 한다.

## 1. 업무 개요와 분기 사이클

전체 프로세스(담당자 확인, 2026-07-15):

1. 기관은 보유 특허를 **지식재산권 마스터**(내부 시스템 추출)로 관리한다.
2. 분기마다 연차료 납부 대행업체(마크프로)가 **납부기한 도래 특허 청구 목록**(엑셀)을 보낸다.
3. 담당자(기술사업화그룹)는 각 특허의 **납부주체**를 판정한다: `연구부서 납부` / `기술사업화그룹` / `조사대상 아님(기업 100% 납부)`. 규칙은 §4, 담당자 재량 건은 예외 목록(§7)·워치리스트(§12)로 관리.
4. **스마트등급 평가 결과**를 반영한다: 도구가 만드는 국가별 조회용 파일(§4.10)로 외부 사이트에서 일괄 조회 → 결과지(.xls)를 도구에 넣어 2차 파일 Y열에 자동 기입(§4.9).
5. 판정 결과로 **1차 업로드 2종**(연구부서=외화→원화 변환, 기술사업화그룹)을 시스템에 업로드한다.
6. **2차 업로드 1종**(연구부서 건 BPM 발명자 의견조회)을 추가 업로드하여 연구자가 시스템으로 유지/포기 여부를 회신한다.
7. 포기 결정 건은 **포기동의서**를 받고, 최종적으로 대행업체에 **납부 지시**한다.
8. 기준연도: 4분기까지 당해연도, 연말에 수행하는 **차년도 1분기 작업은 차년도**를 기준연도로 입력. **1분기는 처리가 다름**(연도, 2차 업로드 파일이 예산조사용 등) — 상세 확정 대기(§9-3).
9. 환율(USD→KRW)은 매 실행 시 수기 입력(자동 조회 없음).

## 2. 아키텍처

```
patent_annuity_tool_v1_4_offline.html   ← 운영 파일 (1.9MB, 단일 파일, 더블클릭 실행, 인터넷 불필요)
 ├─ <script> #1 : ExcelJS 4.4.0 전문 인라인      (xlsx 읽기/쓰기)
 ├─ <script> #2 : JSZip 3.10.1 전문 인라인       (ZIP 다운로드)
 ├─ <script> #3 : SheetJS 0.18.5 전문 인라인     (스마트등급 결과 .xls 읽기 전용, v1.4 신규)
 ├─ <script> #4 : annuity_engine v1.3 전문 인라인 ← annuity_engine_v1_3.js 와 바이트 일치(검증 항목)
 └─ <script> #5 : UI (드래그앤드롭, 파라미터, 예외 파서, 등급 파일 입력, 다운로드/ZIP)
```

- 엔진은 **UMD 패턴**: Node(`require`)와 브라우저(`window.AnnuityEngine`)에서 동일 동작. **검증은 Node, 운영은 브라우저**에서 같은 코드를 실행한다.
- **오프라인 번들 빌드 절차**(v1.3부터): CDN `<script src>`를 제거하고 라이브러리 원문을 인라인한다. 재빌드는 파이썬 치환 스크립트로 수행하며, **모든 치환은 "앵커 문자열이 정확히 1회 존재"를 assert**한 뒤 실행한다(치환 실패를 침묵시키지 않기 위함). 주요 앵커:
  - 엔진 교체: 주석 `Patent Annuity Survey Builder - Core Engine` 를 포함하는 `<script>` 블록 전체를 새 엔진 파일 내용으로 치환
  - 라이브러리 식별: 각 블록 첫 줄 주석 `/* ExcelJS 4.4.0 — 오프라인 내장 ... */` 등
  - 라이브러리 인라인 시 `</script` 문자열을 `<\/script` 로 이스케이프(ExcelJS 내부에 1건 존재)
- **엔진 수정 시 반드시 HTML 재빌드.** HTML 안의 엔진과 별도 js 파일이 어긋나는 것이 가장 흔한 유지보수 사고 지점이다. 재빌드 후 "인라인 엔진 == 표준 js 바이트 일치"를 확인한다(§6.6).

## 3. 입력 사양

### 3.1 마크프로 제공 목록 (File A)

- 헤더 1행, 데이터 2행부터. **데이터 행 판별 = J열(고객관리번호) 비어있지 않음** → 하단 합계 2행(KRW/USD) 자동 제외.
- **표준 36열**(A~AJ). 엔진 상수 `MK_HEAD`에 헤더 고정, 실제와 다르면 `headerIssues` 노트 경고(중단하지 않음).

| 열 | 헤더 | 열 | 헤더 | 열 | 헤더 |
|---|---|---|---|---|---|
| A | 번호 | M | 납부기한일 | Y | 대리인 |
| B | 납부여부 | N | 청구항수 | Z | 대리인명(국문) |
| C | 국가 | O | 비용분담 | AA | 사업장명 |
| D | 권리 | P | 권리인명 | AB | 사업장2 |
| E | 구분 | Q | 예상권리만료일 | AC | 발명의명칭 |
| F | 출원번호 | R | US entity | AD | 발명자이름 |
| G | 출원일자 | S | 예상비용 통화 | AE | 건담당자 |
| H | 등록번호 | T | 예상비용 | AF | 관리소속1 |

- 신규 열 자동 승계(37열~): `extraHeaders`/`extra[]`로 읽어 1차 41열 이후·리포트 구분값 끝에 원값 승계. 2차에는 넣지 않음.
- 값은 전부 문자열(`toStr`), 날짜도 `'2026-10-01'` 문자열 그대로 복사(재서식 금지).

### 3.3 시트 자동탐지 (`findSheets`) — v1.1과 동일

마크프로 후보(1행에 `고객관리번호`+`MARKPRO REF.` 있고 `납부 구분`·`3.연차료 납부 조사 대상` 없음) → 복수 시 납부기한 최댓값 최신 시트. 마스터 후보(1~3행에 B=`관리번호`, Y(25)=`단독/공동`) → 같은 워크북 우선·행수 최다. 핵심 헤더 위치 점검 노트. 열 이동 시 `MC` 수정(§11).

### 3.4 공통 파싱 규칙 — v1.1과 동일

`toStr`(Date는 **UTC getter**로 YYYY-MM-DD, 수식셀→result, richText 연결), `toDate`(앞 10자, 구분자 `-./`), `parseNum`(콤마 제거 parseFloat).

### 3.5 스마트등급 결과 파일 (File C, 선택 — v1.4 신규)

- 외부 평가 사이트에서 내려받는 결과지. **.xls(BIFF)/.xlsx 모두 지원**(SheetJS로 읽음). 암호화 파일 불가.
- **첫 번째 시트만** 읽는다(기존 파이썬 matcher와 동일 가정). 1행=머리글.

### 4.9 스마트등급 매칭 (v1.3 신규)

목적: 외부 평가 결과(File C)의 등급을 조사 대상 특허에 연결해 **2차 업로드 Y열('스마트등급')**에 기입. 정규화 규칙은 담당자 제공 `patent_grade_matcher.py v1.1`을 그대로 이식했다(파이썬↔JS 25개 벡터 동등성 검증, §6.5).

**정규화 키 (MIN_KEY_LEN=6, 미달 시 키 없음 처리)**

```
gradeKeyReg(등록번호):  대문자 → ①선행 영문자 제거(^[A-Z]+: EP, US, ZL …)
                        → ②말미 종류코드 제거([A-Z]\d?$: B1, B2, A …)  ※ 숫자 추출 전에!
                        → ③숫자만 추출 → 길이≥6이면 키
gradeKeyApp(출원번호):  대문자 → ①선행 영문자 제거
                        → ②유럽 체크디짓 제거(\.\d$: ".7" 등)
                        → ③숫자만 추출
                        → ④13자리이고 '10'으로 시작하면 앞 2자 제거(한국 출원 1020190158577→20190158577)
                        → 길이≥6이면 키
숫자 셀: '123.0' 꼬리 없이 정수 문자열로 처리 — xlrd(구 파이썬) float 아티팩트를 재현하지 않음(의도된 개선, §8-11)
```

**매칭 절차**
1. `buildGradeMaps(records)`: 결과지에서 등록키맵·출원키맵 생성. 동일 키에 **서로 다른 원본** 번호가 오면 충돌 목록에 기록하고 **첫 값 유지**(first-wins, 파이썬과 동일 거동).
2. `applyGrades(rows, maps)`: 각 행에 대해 **등록번호(src[7]) 키 우선, 출원번호(src[5]) 키 보조**로 등급 조회 → `row.grade`, `row.gradeSrc`('등록번호'/'출원번호'). 미매칭이고 F≠조사대상아님이면 사유 `스마트등급 미매칭: ...` push(→ 검토필요 시트에 자동 표기).
3. 실행 시점: `classify` **이후** — 분류에 영향 없음(§0-4).

**출력 반영**
- 2차 Sheet1 Y열(25)에 `row.grade` 기입. 등급 기능 활성인데 미매칭인 행은 Y셀 배경 `FFFFF2CC`(연노랑) + 메모 `스마트등급 결과 파일에 해당 특허 없음 → 수동 확인 필요`.

## 12. 특별관리 히스토리 시스템 (v1.0 신설)

### 12.1 목적·설계 원칙

"특이한 특허"(담당자 재량 건, 기업납부 유지 필요 건, 패밀리 유지주의 건 등)의 분기별 이력을 **내부망 오프라인**에서 지속 관리한다. 브라우저는 로컬 파일 제자리 갱신이 불가하므로 이 기능만 **파이썬**으로 분리했다(담당자 PC에 파이썬 설치 확인, 2026-07-15). **도구(HTML)는 일절 수정하지 않아** 업로드 파일 회귀 위험이 0이다 — 히스토리는 도구 산출물인 검토 리포트를 읽기만 한다.

- **의존성 0**: 파이썬 표준 라이브러리만 사용(zipfile+ElementTree로 xlsx 직접 파싱). pip 불필요, 파이썬 3.6+.
- 지원 범위: **본 도구가 생성한 검토 리포트 전용**(sharedStrings/inlineStr/숫자/수식결과). 범용 엑셀 리더가 아님.

### 12.4 스키마(13열)·갱신 규칙

`관리번호, 분기, 분류, 등록후연차, 국가, 납부기한일, 스마트등급, 특별관리사유(;결합), 지정메모, 검토사유(| 결합), 발명의명칭, 기록일시, 도구버전`

- 리포트 의존 시트: `0.실행정보`(분기 라벨·도구 버전), `1.구분값(시트2)`(**헤더 이름으로 열 탐색** — 열 추가·이동에 견딤), `2.검토필요`, `3.스마트등급`(있을 때만; '(미매칭)'은 무시).
